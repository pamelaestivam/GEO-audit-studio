# Implementation plan, November 2026: make the one engine true, measure it for real, give a reason to return

The owner agreed on 2026-11-14 to the recommendations in `docs/STRATEGY_2026-11-14.md`
(`docs/DECISIONS.md`, same date). This file is the specification for the session that
builds them. It is written to be executed by someone with no memory of the analysis.

**Rules that apply to every package:** `CLAUDE.md` in full. One package is one branch
and one pull request, merged (merge commit) before the next package starts, after
green CI, a fresh-context `adversarial-reviewer` run, and an `eval-pm` SHIP. If a
gate is red and cannot be fixed, stop at that package, write why in
`docs/PROGRAM.md`, and say so. Never start a package on top of an unmerged one.

**Order:** P0, P1, P2, P3. P1 is small and lets the owner's part run in parallel.

## P0. Preflight (no pull request)

1. `git remote get-url origin` prints the github.com URL; `git log origin/main..main` is empty.
2. `npm ci && npm run verify`. Record the check count. If it is red on an untouched
   `main`, fix that alone first (I-22) and nothing else.
3. Read this file, `docs/STRATEGY_2026-11-14.md` section 1, `TECH_DEBT.md` 2.19,
   `docs/INSIGHTS.md` I-36 to I-40.

## P1. The engine probe: real answers from real engines, read from a workflow log

**Why:** nothing a real engine returns has ever been checked (`docs/PROGRAM.md` row
10). The workspace cannot reach most provider hosts, but GitHub Actions runners can
(I-15), and the session can start a workflow and read its log.

**Build**

- `scripts/engine-probe.mjs` (plain Node, no new dependency). For each candidate
  whose key is present in the environment, ask a fixed, harmless question list
  (default 2 questions, `--questions N` up to 5; for example "What are the best poke
  restaurants in Austin, Texas?") and print one block per call:
  HTTP status; whether a web search ran; how many sources came back; the names of
  the top-level and second-level fields of the reply (names only); the first 300
  characters of the answer; on an error, the status and the first 500 characters
  of the body. Candidates and the calls to make:
  - **Gemini**, key `PROBE_GEMINI_API_KEY`, for each of `gemini-3.6-flash` and
    `gemini-2.5-flash-lite`: (a) a plain call, no tools; (b) a call with
    `tools: [{ googleSearch: {} }]`; (c) the look-up shape: `googleSearch` together
    with `responseMimeType: 'application/json'` and a small schema (this is what
    `/api/audit/parse-url` sends; older models refused that combination, and whether
    `gemini-2.5-flash-lite` accepts it is unknown).
  - **Mistral**, key `PROBE_MISTRAL_API_KEY`: the Conversations API
    (`/v1/conversations`) with the `web_search` tool, model `mistral-medium-latest`.
    Sources arrive as `tool_reference` chunks with `url` and `title`.
  - **Groq**, key `PROBE_GROQ_API_KEY`: `openai/gpt-oss-120b` with the built-in
    `browser_search` tool, and once without it.
  The API shapes for Mistral and Groq come from their docs as read on 2026-11-14 and
  are unverified; a 4xx that shows the shape is wrong is a result to print, not a
  reason to guess again more than once.
- Never print a key. Scrub every key value from anything printed (make the fake
  failure carry the key and prove it is scrubbed: I-30). At most 20 calls per run in
  total. A candidate with no key prints `SKIP <name>: no key` and the script exits 0;
  with no key at all it exits 0 and says so.
- `.github/workflows/engine-probe.yml`: `workflow_dispatch` only (never on push,
  pull request or schedule), inputs `questions` (default 2) and `candidates`
  (default all), `permissions: contents: read`, secrets passed by name, the full
  replies saved as a workflow artifact (`probe-<run id>.json`, keys scrubbed).
- `test/engineProbe.test.ts`: the script against local fake servers for each
  provider (a searched reply, a refused search, a plain reply, a 401), asserting the
  printed blocks and that a key never appears. Add it to the `npm test` chain and to
  the commands list in `CLAUDE.md`.
- `docs/PROGRAM.md`: owner action **O-8**, numbered steps: create the repository
  secret `PROBE_GEMINI_API_KEY` (the same free key as on Vercel); optionally a free
  Mistral key and a free Groq key (no card for either; if either site asks for a
  card, stop and tell the assistant) as `PROBE_MISTRAL_API_KEY` and
  `PROBE_GROQ_API_KEY`. Say why only the owner can do it (secrets cannot be set from
  the session) and that the probe makes at most 20 free calls per run.

**After merge:** start the workflow with the GitHub tool (`actions_run_trigger`) and
read the log. If the secrets are not there yet the run prints SKIP lines: that is
fine, go on to P2 and start it again at the end of the session. When real results
exist: write them into `docs/INSIGHTS.md` (MEASURED), the verification ledger in
`docs/PROGRAM.md`, and save one scrubbed real reply per provider under
`test/fixtures/real/` for P2 and later adapters.

**Done when:** merged; the test fails if scrubbing is removed; the workflow has been
started once and its outcome (results or SKIP) is recorded.

## P2. A refused or missing web search is visible and true (closes `TECH_DEBT.md` 2.19)

**Why:** section 1 of the strategy. Today a refused search reads as a quota problem,
the readiness check cannot see it, and an answer given without a search is scored.

**Behaviour to build**

1. **Every answer records whether a search ran.** `QueryEvidence` gains
   `searched: boolean`. Gemini: true when the reply has at least one web search
   query or at least one grounding chunk. ChatGPT: a `web_search_call` item or a URL
   annotation. Perplexity: a non-empty `search_results` or `citations`. Claude: a
   `server_tool_use` block. Decide it in one small pure function per engine, unit
   tested.
2. **An answer with text but no search is not counted.** It becomes a failed
   look-up with `errorKind: 'not_searched'` and exactly this sentence:
   `<Engine> answered without searching the web, so this answer was not counted.`
   It travels the existing failure paths (the "n of M" denominators, the per-engine
   reason in the matrix, the all-failed audit). `metricVersion` becomes 3; reports
   saved under 2 say they were measured before unsearched answers were excluded
   (extend `metricVersionNote`); `src/reportGuard.ts` accepts 3. Update the golden
   reports with `UPDATE_GOLDEN=1` and read the diff: only `metricVersion` and the
   new field may change.
3. **A refused search gets its own state and sentence, separate from quota.** New
   pure module `src/searchAvailability.ts` (no network, injected clock), states
   `unknown | available | refused(until)`. In `generateContentWithRetry`, when a
   call that asked for `googleSearch` fails with a quota or rate-limit error:
   - if the raw error names a zero limit (`limit: 0`) on a search or grounding
     quota, it is refused: no probe needed;
   - otherwise make ONE plain call (no tools, the same model, "Reply with the single
     word OK."), counted by the call counter and the daily cap like any other. If
     the plain call succeeds, the search is refused. If it fails too, it is an
     ordinary quota or rate limit and today's behaviour stands.
   A refused search does **not** trip the quota breaker (plain calls still work).
   While the state is `refused`, further searched calls fail at once without a
   network call. The state lasts 30 minutes if no searched call has ever succeeded
   in this process or, on a durable store, in the last 24 hours of steps; otherwise
   until midnight Pacific (a used-up daily search allowance looks the same from
   outside, and that one does reset).
   The sentence says only what is known. Never succeeded:
   `Gemini accepted this key but refused to search the web with the model <model>, and no searched answer has ever come back from it on this server. Google's free plan offers web search only on some models, so waiting is unlikely to fix this. Ask the operator to set GEMINI_MODEL to a model whose plan includes Google Search, then re-run.`
   Succeeded before:
   `Gemini accepted this key but refused to search the web with the model <model>. Searched answers came back earlier, so the day's free search allowance is probably used up; it resets at midnight Pacific time.`
   `errorKind: 'search_refused'`. `/api/audit/status` reports the state.
4. **The readiness check asks what an audit asks.** Keep the plain call and add a
   `gemini search` check that makes one searched call and is ok only when the reply
   shows a search ran. Both are cached for five minutes as today and counted. A plain
   pass with a search failure prints the sentence above. `scripts/smoke.mjs` shows
   the new line. Update the call count stated in `docs/PROGRAM.md` O-3 step 4.
5. **The default model becomes `gemini-2.5-flash-lite`** (`DEFAULT_GEMINI_MODEL`),
   the only model Google lists with free web search that is not being withdrawn
   (READ 2026-11-14; if P1 produced real results that contradict this, follow the
   results and say so). The owner agreed to this change of the model the report
   names. State in the pull request's first line that the live site will ask a
   different model after the merge.
6. **The report says how it measured.** Wherever engines are named with their model,
   add once: `Measured through each engine's API, which can differ from what its app shows.`
   Add the same sentence, with one more of explanation, to `docs/USER_GUIDE.md`.

**Proof (the repository's template: the built server, a fake Gemini that counts hits)**

- `test/fakeGemini.ts` gains modes: `search_refused` (HTTP 429 with the body
  `{"error":{"code":429,"message":"You exceeded your current quota, please check your plan and billing details.","status":"RESOURCE_EXHAUSTED"}}`
  when the request carries the search tool, a normal reply otherwise);
  `search_refused_zero` (the same with `limit: 0` and a search quota metric in the
  message); `unsearched_answer` (HTTP 200, text, no grounding metadata).
- `test/searchAvailability.test.ts` (pure) and `test/searchRefusedE2E.test.ts`
  (built server). The end-to-end file proves, by counting real hits:
  one question under `search_refused` makes exactly 2 calls (the searched one and
  the one plain probe), the audit ends failed with the never-succeeded sentence and
  not the quota sentence, the quota breaker is not tripped, and a second audit
  inside the window makes 0 calls; under `search_refused_zero` exactly 1 call;
  after a successful searched audit, a later refusal gives the succeeded-before
  sentence; under `unsearched_answer` the answer is "0 of 1", listed as not counted
  with its sentence, and the audit is not reported as "the engine left you out";
  readiness shows plain ok and search failed.
- Break each protection once and watch a check fail (list what was broken in the
  pull request): the plain probe removed, the breaker tripped anyway, the
  `searched` rule returning true always, the readiness search call made without the
  tool.
- `ux-tourist` on the failed-audit and not-counted screens, desktop and phone.

**Records:** close `TECH_DEBT.md` 2.19 against the tests; `CLAUDE.md` (the quota

## P3. Run an audit again and show what changed

**Why:** the reason anyone returns (`TECH_DEBT.md` 3.1, `docs/MVP_AUDIT.md` item 17).
History is durable now, so the comparison can be honest.

**Behaviour to build**

1. A saved audit has a **Run again** action. It reuses exactly the saved inputs and
   the saved question texts (no regeneration, no look-up), goes through the normal
   submit path (idempotency key, budgets, the step plan), and the new job stores
   `previousAuditId`. Ownership is enforced: only the owner of the first audit can
   re-run it.
2. A pure function `compareReports(previous, next)` in `src/reportCompare.ts`:
   - refuses to call it a change when the two are not comparable, and says which
     reason applies: different `metricVersion`, a different engine model, a
     different question list, or either audit failed. In that case the page shows
     the two side by side with the sentence
     `These two audits were not measured the same way (<reason>), so the difference is not shown as a change.`
   - when comparable: per question and engine, named before and named now; the
     visibility as "n of M" for both, never a bare percentage and never a percentage
     difference when M is under 3 (decision D); sources that appeared and sources
     that went; competitors newly named. Failed look-ups on either side are listed
     as "not measured this time", never as a loss.
   - one answer differing between two runs is normal variation, so the strip carries
     the sentence `Answer engines vary from run to run; a change in one answer is an observation, not a trend.`
3. The saved-audit page shows a "Since the previous run" strip built only from that
   function. No number in it comes from anywhere else.

**Proof:** `test/reportCompare.test.ts` (pure: every non-comparable reason, empty and
one-question audits, a failed look-up on each side, identical runs); an end-to-end
test on the built server with a fake Gemini that changes its answer between two runs
(calls counted: a re-run costs exactly what the plan says); the browser suite on
desktop and phone; `ux-tourist`.

**Done when:** merged; `docs/USER_GUIDE.md` explains the strip; `TECH_DEBT.md` 3.1 and
`docs/MVP_AUDIT.md` item 17 updated.
