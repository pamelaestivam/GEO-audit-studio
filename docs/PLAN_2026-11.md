# Implementation plan, November 2026: make the one engine true, measure it for real, give a reason to return

The owner agreed on 2026-11-14 to the recommendations in `docs/STRATEGY_2026-11-14.md`
(`docs/DECISIONS.md`, same date). This file is the specification for the session that
builds them. It is written to be executed by someone with no memory of the analysis.
A fresh-context review of its first version found defects that would have broken
existing behaviour; this version is the corrected one (`docs/SESSION_LOG.md`, 2026-11-14).

**Rules that apply to every package:** `CLAUDE.md` in full. One package is one branch
and one pull request, merged (merge commit) before the next package starts, after
green CI, a fresh-context `adversarial-reviewer` run, and an `eval-pm` SHIP. If a
gate is red and cannot be fixed, stop at that package, write why in
`docs/PROGRAM.md`, and say so. Never start a package on top of an unmerged one.

**Existing tests are the contract.** No package may loosen, delete or skip an
existing check to get green. Where this plan says a pinned value changes on purpose,
it names the test; any other red test means the change is wrong, not the test.

**Order:** P0, P1, P2, P3. P1 is small and lets the owner's part run in parallel.
(The strategy listed "run again and show what changed" after the owner's first real
audits. It is built here as P3 because it needs no key and the owner's real audits
are where a before-and-after is first wanted. The order of the owner's own steps is
unchanged.)

## P0. Preflight (no pull request)

1. `git remote get-url origin` prints the github.com URL; `git log origin/main..main` is empty.
2. `npm ci && npm run verify`. Record the check count. If it is red on an untouched
   `main`, fix that alone first (I-22) and nothing else.
3. Read this file, `docs/STRATEGY_2026-11-14.md` section 1, `TECH_DEBT.md` 2.19,
   `docs/INSIGHTS.md` I-36 to I-40.

## P1. The engine probe: real answers from real engines, read from a workflow log

**Why:** nothing a real engine returns has ever been checked (`docs/PROGRAM.md` row
10). The workspace cannot reach most provider hosts, but GitHub Actions runners can
(I-15), and the session can start a workflow and read its log.

**Build**

- `scripts/engine-probe.mjs` (plain Node, no new dependency). For each candidate
  whose key is present in the environment it asks a fixed, harmless question list
  (`--questions N`, default 2, at most 3; for example "What are the best poke
  restaurants in Austin, Texas?") and prints one block per call: HTTP status;
  whether a web search ran; how many sources came back; the names of the top-level
  and second-level fields of the reply (names only); the reply itself, cut at 4,000
  characters; on an error, the status and the first 500 characters of the body.
  Candidates and calls:
  - **Gemini**, key `PROBE_GEMINI_API_KEY`, for each of `gemini-3.6-flash` and
    `gemini-2.5-flash-lite`: (a) ONE plain call, no tools; (b) N calls with
    `tools: [{ googleSearch: {} }]`; (c) ONE call in the look-up shape:
    `googleSearch` together with `responseMimeType: 'application/json'` and a small
    schema. Shape (c) is what `/api/audit/parse-url` and
    `/api/audit/generate-queries` send (`server.ts`); older models are believed to
    refuse it, and whether `gemini-2.5-flash-lite` accepts it is unknown. P2 depends
    on this answer.
  - **Mistral**, key `PROBE_MISTRAL_API_KEY`: N calls to the Conversations API
    (`/v1/conversations`) with the `web_search` tool, model `mistral-medium-latest`.
    Sources arrive as `tool_reference` chunks with `url` and `title`.
  - **Groq**, key `PROBE_GROQ_API_KEY`: N calls to `openai/gpt-oss-120b` with the
    built-in `browser_search` tool, and ONE without it.
  That is 2N+4 Gemini calls, N Mistral, N+1 Groq: 13 at N=2, 17 at N=3. The script
  refuses to start a run that would exceed 20 calls and says so; it never drops a
  candidate silently.
  The Mistral and Groq request shapes come from their docs as read on 2026-11-14 and
  are unverified: a 4xx that shows the shape is wrong is a result to print. Correct
  a shape at most once from the error text; do not iterate on guesses.
- **The log is public** (the repository is public, I-15). Never print a key, and
  scrub from everything printed: every key value, anything matching
  `projects/<digits>`, and any run of ten or more digits. Make the fake failure
  carry the key and a project number and prove both are scrubbed (I-30). No
  artifact is uploaded: the scrubbed log is the record.
- A candidate with no key prints `SKIP <name>: no key`; with no key at all the
  script prints that and exits 0.
- `.github/workflows/engine-probe.yml`: `workflow_dispatch` only (never push, pull
  request or schedule), inputs `questions` (default 2) and `candidates` (default
  all), `permissions: contents: read`, secrets passed by name. Use only the actions
  the other workflows already use, with the same pinned commits copied from them;
  never type a commit hash from memory.
- `test/engineProbe.test.ts`: the script against local fake servers for each
  provider (a searched reply, a refused search, a plain reply, a 401), asserting the
  printed blocks, the call budget refusal, and that neither a key nor a project
  number appears. Add it to the `npm test` chain and to the commands list in
  `CLAUDE.md`.
- `docs/PROGRAM.md`: owner action **O-8**, numbered steps: add the repository secret
  `PROBE_GEMINI_API_KEY` (the same free key as on Vercel); optionally a free Mistral
  key and a free Groq key as `PROBE_MISTRAL_API_KEY` and `PROBE_GROQ_API_KEY` (if
  either site asks for a card, stop and tell the assistant). Say why only the owner
  can do it (a session cannot set secrets), that each run makes at most 20 free
  calls, and that the log is public and shows the question and the engines' answers,
  never a key.

**After merge:** start the workflow with the GitHub tool (`actions_run_trigger`; if
the tool refuses, say so and give the owner the two clicks) and read the log. If the
secrets are not there yet the run prints SKIP lines: that is a valid outcome. When
real results exist, write them into `docs/INSIGHTS.md` (MEASURED) and the
verification ledger in `docs/PROGRAM.md`, and save one scrubbed real reply per
provider under `test/fixtures/real/`.

**Done when:** merged; the test fails if scrubbing is removed; the workflow has been
started once and its outcome (results or SKIP) is recorded.

## P2. A missing or refused web search is visible and true (closes `TECH_DEBT.md` 2.19)

**Why:** section 1 of the strategy. Today an answer given without a search is
scored like a searched one, the readiness check asks without search, and a refused
search reads as an ordinary quota problem.

**What must NOT change.** How a 429 is handled inside `generateContentWithRetry`
(`server.ts`): the wait-and-retry on a stated delay, when the breaker trips, and
how many calls each case makes. These are pinned by `test/retrySpendE2E.test.ts`,
`test/quotaBreakerE2E.test.ts`, `test/quotaEfficiencyE2E.test.ts` and
`test/auditStepsE2E.test.ts`, and each pin is a bug that shipped. **This package
adds no call to any audit, look-up or retry path.** The only new calls are in the
readiness check (item 4).

**Behaviour to build**

1. **Every answer records whether a search ran.** `QueryEvidence` gains
   `searched: boolean`. Gemini: true when the reply has at least one web search
   query or at least one grounding chunk. ChatGPT: a `web_search_call` item or a URL
   annotation. Perplexity: a non-empty `search_results` or `citations`. Claude: a
   `server_tool_use` block. One small pure function per engine, unit tested.
2. **An answer with text but no search is not counted.** It becomes a failed
   look-up with `errorKind: 'not_searched'` and exactly this sentence:
   `<Engine> answered without searching the web, so this answer was not counted.`
   The sentence is true whether the engine chose not to search or could not. It
   travels the existing failure paths (the "n of M" denominators, the per-engine
   reason in the matrix, the all-failed audit). `metricVersion` becomes 3
   (`src/auditPipeline.ts`); reports saved under 2 say they were measured before
   unsearched answers were excluded (`src/reportView.ts`: `isEarlierMetricRule` and
   `metricVersionNote` know one earlier rule today and must know two, each with its
   own sentence; `src/reportGuard.ts` has text that names version 2).
   Pinned values that change on purpose: `metricVersion` in the thirteen golden
   reports (`UPDATE_GOLDEN=1`, then read the diff: nothing else may differ unless
   item 5 applies).
   Record in `TECH_DEBT.md` that how often a real engine answers without searching
   is unknown until P1's probe has run; if it is common, this rule is revisited with
   the owner.
3. **A refused search is a state of its own, learned without extra calls.** New pure
   module `src/searchAvailability.ts` (no network, injected clock), states
   `unknown | available | refused`, fed only by things that already happen:
   - a searched Gemini call that comes back with `searched: true` sets `available`
     and records the time;
   - a searched call whose error names a zero limit (`limit: 0`) on a search or
     grounding quota sets `refused` for 30 minutes;
   - the readiness check (item 4) finding "plain call ok, searched call refused"
     sets `refused` for 30 minutes.
   While `refused`, a searched call fails at once without a network call, with
   `errorKind: 'search_refused'` and exactly:
   `Gemini accepted this key but refused to search the web with the model <model>. Google's free plan offers web search only on some models, and a used-up daily search allowance looks the same from outside. Ask the operator to run the readiness check, which tells the two apart, or to set GEMINI_MODEL to a model whose plan includes Google Search.`
   A refused search never trips the quota breaker. The state is per process and is
   lost on restart; say so in the code and in `/api/audit/status`, which reports
   `geminiSearch: { state, lastSearchedAt }` (in this process only).
   In every other case a 429 keeps today's sentence and today's behaviour. The page
   adds one separate line under a failed audit, only when the failure kind is quota
   or rate limit and the status says no searched answer has come back since this
   server started:
   `No searched answer has come back from this model since this server started. If audits keep failing this way, the model may have no free web search on this key; the operator's readiness check tells.`
4. **The readiness check asks what an audit asks.** Keep the plain call. Add a
   `gemini search` check: one call with the search tool and the audit's own system
   instruction, asking a question that needs the web
   (`What are the best-rated poke restaurants in Austin, Texas right now? Name three.`),
   ok only when the reply shows a search ran. Results: both ok; plain ok and search
   refused (prints the refused sentence and sets the state); plain ok and answered
   without searching (`Gemini answered the readiness question without searching the web.`,
   not ok); plain failed (today's behaviour, the search call is not made).
   Both are cached five minutes as today, counted by the call counter and refused by
   the daily cap like any call. `scripts/smoke.mjs` prints the new line. Update the
   number of calls stated in `docs/PROGRAM.md` O-3 step 4 (two per readiness run,
   not one).
5. **The default model changes only on a measurement.** `DEFAULT_GEMINI_MODEL`
   becomes `gemini-2.5-flash-lite` in this package **only if** P1's probe has
   MEASURED, on the owner's key, that it answers a searched call. Then:
   - if the probe also shows the look-up shape (c) is accepted: change the default,
     nothing more;
   - if shape (c) is refused: change the default, and in the same package make
     `/api/audit/parse-url` and `/api/audit/generate-queries` answer a refusal of
     that shape with a true sentence
     (`Automatic detection is not available with the model this server uses. Type the details yourself; nothing was filled in.`)
     using the real error body from the probe as the fixture. Do not redesign the
     look-ups here; write the follow-up into `TECH_DEBT.md`.
   - if there are no probe results (the secrets are not there): **do not change the
     default.** Everything else in this package ships. The owner's `GEMINI_MODEL`
     variable (`docs/PROGRAM.md` O-7) stays the lever, and `docs/PROGRAM.md` says the
     default waits on O-8.
   Pinned values that change on purpose when the default changes: the model id in
   eleven golden reports, `test/mvpHardeningE2E.test.ts` and
   `test/reportView.test.ts`. State in the pull request's first line that the live
   site will ask a different model after the merge.
6. **The report says how it measured.** Where engines are named with their model,
   add once: `Measured through each engine's API, which can differ from what its app shows.`
   Add the same sentence, with one more of explanation, to `docs/USER_GUIDE.md`.

**Proof (the repository's template: the built server, a fake Gemini that counts hits)**

- `test/fakeGemini.ts`: **first** make the fake return grounding metadata only when
  the request carries the search tool (today every 200 reply carries it, so a
  "searched" check could never fail). Run the whole suite on that change alone; a
  test that goes red was relying on grounding in a tool-less reply and is a finding
  to understand, not to paper over. Then add modes: `search_refused_zero` (HTTP 429
  whose message names a search quota with `limit: 0`, when the request carries the
  tool; a normal reply otherwise), `search_refused` (the same without `limit: 0`:
  `You exceeded your current quota, please check your plan and billing details.`),
  `unsearched_answer` (HTTP 200, text, no grounding metadata even with the tool).
- `test/searchAvailability.test.ts` (pure) and `test/searchRefusedE2E.test.ts`
  (built server, hits counted):
  - `unsearched_answer`: one question gives "0 of 1", the answer listed as not
    counted with its sentence, never "the engine left you out"; the call count is
    exactly what the same audit costs today.
  - `search_refused_zero`: the audit fails with the refused sentence, the quota
    breaker is not tripped, a second audit inside 30 minutes makes 0 calls, and
    `/api/audit/status` shows `refused`.
  - `search_refused`: the audit behaves exactly as a rate-limited audit does today
    (same sentence, same call count), plus the separate line; then the readiness
    check finds "plain ok, search refused", and the next audit fails at once with
    the refused sentence and 0 calls.
  - readiness: each of the four results above, with the number of calls each makes.
  - the existing quota, retry, efficiency and step suites pass unchanged.
- Break each protection once and watch a check fail (list them in the pull
  request): `searched` always true; the breaker tripped on a refusal; the readiness
  search call sent without the tool; the readiness result not feeding the state.
- `ux-tourist` on the failed-audit and not-counted screens, desktop and phone.

**Records:** close `TECH_DEBT.md` 2.19 against the tests; `CLAUDE.md` (the quota
section, the engine table, the commands list); `docs/DEPLOYMENT.md`; `.env.example`;
`docs/PROGRAM.md` row 13; a `docs/DECISIONS.md` entry for `metricVersion` 3 and, if
it changed, the default model.

**Done when:** merged, and after the merge the daily live check (or a manual start
of it) is read and its outcome recorded.

## P3. Run an audit again and show what changed

**Why:** the reason anyone returns (`TECH_DEBT.md` 3.1, `docs/MVP_AUDIT.md` item 17).
History is durable now, so the comparison can be honest.

**Behaviour to build**

1. A saved audit has a **Run again** action. It reuses exactly the saved inputs and
   the saved question texts (no regeneration, no look-up), goes through the normal
   submit path (idempotency key, budgets, the step plan), and the **saved report**
   of the new audit carries `previousAuditId` (job rows are pruned after a week, so
   the link cannot live on the job). Only the owner of the first audit can re-run
   it; anyone else gets the same answer as for an audit that does not exist.
2. A pure function `compareReports(previous, next)` in `src/reportCompare.ts`:
   - it refuses to call it a change when the two are not comparable, and names the
     reason: a different `metricVersion`, a different engine model, a different
     question list, or either audit failed. The page then shows the two side by
     side with
     `These two audits were not measured the same way (<reason>), so the difference is not shown as a change.`
   - when comparable, everything is computed **only over question-and-engine pairs
     measured in both runs**: named before and named now; visibility as "n of M"
     for both runs over those pairs, as counts, with no percentage difference;
     sources that appeared and sources that went; competitors newly named. A pair
     that failed in either run is listed as `not measured in one of the two runs`
     and contributes nothing else: a failed look-up must never show its sources as
     gone.
   - the strip always carries
     `Answer engines vary from run to run; a change in one answer is an observation, not a trend.`
3. The saved-audit page shows a "Since the previous run" strip built only from that
   function. If the earlier audit has been deleted the strip says
   `The earlier audit this one was compared with has been deleted.` and shows nothing else.

**Proof:** `test/reportCompare.test.ts` (pure: every non-comparable reason, empty and
one-question audits, a failed look-up on each side with its sources, identical runs,
a deleted earlier audit); an end-to-end test on the built server with a fake Gemini
that changes its answer between two runs (calls counted: a re-run costs exactly what
the plan says; a second user cannot re-run or read the link); the browser suite on
desktop and phone; `ux-tourist`.

**Done when:** merged; `docs/USER_GUIDE.md` explains the strip; `TECH_DEBT.md` 3.1 and
`docs/MVP_AUDIT.md` item 17 updated.

  write the next plan; do not adopt an engine on documentation alone.
- **Reliability slices S6 and S7:** held until real audits exist (`docs/DECISIONS.md` 2026-11-14).
- **The engineering backlog** (`docs/ENGINEERING_BACKLOG.md`): a separate session.
